원본 메모리 유지가 의도보다 길어졌다면 ROI/Share가 아직 살아 있는지 확인하세요. 외부 스레드와 수정 가능한 데이터의 동시 사용 안전성은 별도 계약 확인 없이 추정해서는 안 됩니다.

관련: ROI · 객체 수명 · ZImage

원리와 입력

수명만 분리하고 같은 픽셀을 읽을 때는 Share를, 선택 범위를 제한하고 원점이 필요한 경우에는 ROI를 검토합니다. 원본과 독립된 저장소가 필요하면 깊은 복사를 선택합니다. 화면이나 파일 전송에 언어 배열이 필요한 상황이라면 packed 복사 또는 해당 형식의 배열 읽기 결과를 사용할 수 있습니다. 이 선택은 연산의 빠르기만이 아니라 이후 누가 어떤 객체를 얼마나 보유하는지에 따라 달라집니다.

적용과 확인

사용이 끝났는데 저장소가 계속 유지된다면 원본 외에도 공유 영상과 ROI가 살아 있는지 확인하세요. 예기치 않은 오류는 반대로 이미 닫힌 객체를 다시 사용했기 때문일 수 있습니다. 작은 영상으로 원본 생성, 별도 핸들 획득, 원본 종료, 남은 객체 읽기, 남은 객체 종료 순서를 기록하면 문제 위치를 확인할 수 있습니다. 실장비 처리량과 실제 메모리 사용은 별도로 측정해야 합니다.

값과 판독 기준

단계입력 또는 결과확인할 점
수명 분리Share동일 픽셀 저장소
부분 선택ROI보이는 크기와 origin
저장소 분리깊은 복사독립 픽셀
메모리 유지남은 핸들Share·ROI·결과를 추적

적용할 때 살펴볼 점

별도 작업에 값을 전달한다면 상대가 필요한 것이 영상 메타데이터인지 픽셀 배열만인지도 확인하세요. ROI의 origin이 필요한데 값만 복사하면 위치 관계를 별도로 보존해야 합니다. 수명 추적 시 원본을 정리한 직후뿐 아니라 마지막 Share와 ROI를 정리한 시점까지 확인하면 저장소가 계속 참조되는 이유를 이해하기 쉽습니다.
