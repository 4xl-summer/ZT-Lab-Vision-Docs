해제와 동시 접근의 확인 범위

C#의 QueryBuilder는 계획 변경·복제·실행·Dispose를 같은 인스턴스 잠금 안에서 처리합니다. 따라서 해당 구현에서 먼저 잠금을 얻은 호출이 끝난 다음 다른 호출이 진행됩니다. 해제가 먼저 완료된 뒤 호출하면 ObjectDisposedException입니다. 실행 결과의 획득과 Dispose도 해당 실행 객체의 잠금으로 보호되며, 먼저 얻은 독립 영상과 값은 실행 해제 후에도 유효합니다. Python의 typed 실행도 output/get_image와 close를 같은 잠금으로 처리하며 닫힌 실행은 ValueError입니다. 이는 확인한 래퍼 메서드의 범위이지 모든 객체, 외부 버퍼, 같은 핸들에 대한 임의의 동시 수정이나 순서까지 보장하는 일반 계약은 아닙니다. 작업별 소유권과 종료 순서를 명시하세요.

원리와 입력

공유 저장소에 독립 핸들이 있다는 것은 모든 동시 접근을 무조건 허용한다는 뜻은 아닙니다. 확인된 관리형 Query 빌더는 변경과 실행, 복제와 해제를 해당 인스턴스의 잠금으로 처리합니다. 실행 객체에서 먼저 취득한 독립 영상은 실행 종료 후에도 사용할 수 있지만, 이미 종료된 실행에 새 출력을 요청하면 해당 언어의 닫힌 객체 오류가 발생합니다.

적용과 확인

Python typed 실행에서는 close 이후 접근이 ValueError이고 C#에서는 Dispose 이후 접근이 ObjectDisposedException입니다. 이 관찰은 지정된 래퍼 호출의 범위입니다. 외부 버퍼의 수정이나 서로 다른 객체를 통한 쓰기 경합의 순서는 이 설명으로 추론하지 마세요. 생산 파이프라인에서는 작업별 소유자와 반환 시점을 정하고, 이미지 핸들의 마지막 사용을 확인한 후 각 핸들을 정리하는 방식으로 흐름을 설계합니다.

공유 핸들의 생존과 픽셀 저장소

실행에서 독립 영상 핸들 B를 먼저 얻었다면 실행 A를 정리해도 B는 자신의 소유권으로 남습니다. 이때 독립적인 것은 핸들의 수명이며, B가 픽셀 저장소를 다른 영상과 공유할 수 있다는 점은 별개입니다. 두 핸들의 픽셀 값이 같다는 사실만으로 별도 저장소인지 판단할 수 없고, 저장소까지 분리해야 한다면 해당 영상의 깊은 복사 계약을 사용합니다.

반대로 실행 A의 정리가 먼저 완료되었다면 그 A에서 새 B를 취득하는 호출은 닫힌 객체 오류가 됩니다. 성공적으로 취득한 B만 별도로 정리하고, 취득에 실패했다면 존재하지 않는 B를 후속 영상 처리에 넘기지 않습니다. 같은 저장소를 가리킨다는 이유만으로 외부 버퍼 쓰기나 서로 다른 객체의 동시 수정 순서가 보장되는 것은 아니므로, 그런 작업은 사용하는 객체와 버퍼의 구체 계약을 따로 확인해야 합니다.
