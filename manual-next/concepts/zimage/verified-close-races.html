해제와 동시 접근의 확인 범위

C#의 QueryBuilder는 계획 변경·복제·실행·Dispose를 같은 인스턴스 잠금 안에서 처리합니다. 따라서 해당 구현에서 먼저 잠금을 얻은 호출이 끝난 다음 다른 호출이 진행됩니다. 해제가 먼저 완료된 뒤 호출하면 ObjectDisposedException입니다. 실행 결과의 획득과 Dispose도 해당 실행 객체의 잠금으로 보호되며, 먼저 얻은 독립 영상과 값은 실행 해제 후에도 유효합니다. Python의 typed 실행도 output/get_image와 close를 같은 잠금으로 처리하며 닫힌 실행은 ValueError입니다. 이는 확인한 래퍼 메서드의 범위이지 모든 객체, 외부 버퍼, 같은 핸들에 대한 임의의 동시 수정이나 순서까지 보장하는 일반 계약은 아닙니다. 작업별 소유권과 종료 순서를 명시하세요.

같은 객체에서 읽기와 해제를 동시에 요청할 때의 순서를 임의로 정해 두면 안 됩니다. 확인된 C# 쿼리 빌더에서는 계획 변경, 복제, 실행과 Dispose가 그 빌더의 잠금 안에서 처리됩니다. 실행 객체에서도 출력이나 캡처 획득과 해제가 같은 객체의 잠금으로 보호됩니다. 먼저 해제가 끝난 객체에 다시 접근하면 닫힌 객체 오류가 발생하며, 먼저 독립적으로 획득한 이미지는 자기 수명을 유지합니다.

Python의 typed 실행도 출력 획득과 close에 해당 객체의 잠금을 사용하며, 닫힌 실행에서 새 값을 얻으려 하면 오류를 냅니다. 이 설명은 확인한 래퍼와 메서드 범위에 한정됩니다. 외부에서 수정 가능한 버퍼나 다른 객체의 임의 동시 사용이 모두 안전하다는 뜻은 아닙니다. 처리 작업이 끝난 뒤 해제하는 명시적인 소유 순서를 설계하는 것이 중요합니다.

예를 들어 완료 작업이 보관한 이미지를 다음 스레드에 전달해야 한다면 먼저 독립 임대를 얻고, 그 임대를 받는 쪽의 해제 책임을 정합니다.

경합 시 두 가지 순서

독립 임대를 얻는 작업과 원본을 해제하는 작업이 같은 래퍼 객체에서 겹치면 실제로 어느 쪽이 먼저 잠금을 얻었는지에 따라 관찰되는 순서가 달라집니다. 확인한 C# ZImage의 Share와 Dispose는 그 객체의 잠금을 사용합니다. Share가 먼저 완료되어 독립 영상이 반환되었다면 이후 원본 해제가 그 새 객체를 자동으로 닫지 않습니다. 반대로 Dispose가 먼저 완료된 뒤 Share를 부르면 닫힌 원본에 대한 접근 오류가 발생합니다.

QueryExecution의 출력 획득과 Dispose도 해당 실행 객체의 잠금에서 이루어집니다. 출력 획득이 성공한 뒤 결과를 닫는 경우와 닫힌 결과에서 새 출력을 얻으려는 경우를 같은 테스트로 뭉뚱그리지 말아야 합니다. 관리형 값 스냅샷을 해제 전에 읽어 보관했다면 실행 객체의 이후 해제와 별개로 그 값을 사용할 수 있습니다.

이러한 설명은 명시한 래퍼 메서드에서 확인한 잠금 범위입니다. 모든 SDK 객체 또는 외부 변경 가능한 버퍼가 임의의 동시 접근을 보장한다는 결론은 아닙니다. 안전한 전달을 위해 작업이 필요한 독립 임대를 먼저 얻고, 작업자가 사용을 마친 뒤 각 소유자가 자신의 객체를 정리하도록 책임을 정합니다.
