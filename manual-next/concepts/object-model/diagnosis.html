8. 흔한 설계 실수와 확인 방법

문제원인확인
결과를 찾았으나 표시 위치가 다름ROI 지역 좌표를 원본 좌표로 사용Position vs GlobalPosition과 origin 확인
영상 메모리 증가결과 ZImage/모델·Query 핸들을 계속 보유프레임 단위 Dispose/close 확인
Query의 한 분기가 다른 분기까지 변경C#/Python의 동일 가변 Builder 참조독립 Clone/clone 사용
매치가 0개정상 빈 결과를 예외 또는 잘못된 결과로 해석Best/None과 오류를 구분
i검증: Rust 공개 Facade, C# 및 Python Wrapper의 메서드명과 수명 의미를 대조했습니다. 새로운 SDK 실행이나 실장비 테스트는 이번 문서 개정에서 진행하지 않았습니다.

관련 문서: ZImage 객체 상세 · ROI · Share/복사 · 수명 · 결과 객체.

원리와 입력

화면에 검출 결과가 어긋나면 먼저 알고리즘 점수보다 좌표 프레임을 확인합니다. ROI 안의 위치는 로컬 좌표이고, 원본 화면에 그릴 때는 해당 원점을 반영한 전역 위치가 필요합니다. ROI 시작점이 (1,0)이고 로컬 위치가 (0,1)이면 원본 위치는 (1,1)입니다. 위치와 origin을 함께 기록하면 모델이 실패한 경우와 표시 좌표만 잘못된 경우를 구분할 수 있습니다.

적용과 확인

프레임마다 메모리가 늘면 결과 영상뿐 아니라 모델, Query 계획, 실행과 취득한 캡처의 해제 지점을 추적하세요. 조건 분기가 예상과 다르면 C#/Python 빌더를 공유했는지 살펴보고 Clone으로 분리합니다. 검색 결과가 비었다면 Best가 없는 정상 상태인지, 입력과 설정이 잘못되어 예외가 발생했는지부터 나눕니다. 실제 설비의 진단은 이 합성 예제만으로 대신할 수 없으며 사용한 SDK와 실행 환경의 기록을 함께 살펴야 합니다.

값과 판독 기준

단계입력 또는 결과확인할 점
위치 어긋남ROI origin로컬·전역 필드 확인
핸들 증가결과·캡처 누락프레임마다 해제 범위 확인
분기 오염가변 계획 공유변경 전 clone
매치 없음빈 결과 또는 예외상태와 오류를 분리

적용할 때 살펴볼 점

문제를 재현할 때는 입력과 설정을 한 번에 많이 바꾸지 마세요. 작은 배열과 알려진 ROI 하나에서 기대 위치를 계산한 뒤 결과를 기록합니다. 그다음 해제 지점이나 Query 분기만 바꾸면 어떤 조건이 영향을 주었는지 확인할 수 있습니다. 빈 결과, 호출 예외, 잘못된 표시 좌표는 서로 다른 관찰이므로 하나의 실패 코드로 뭉치지 않는 편이 좋습니다.
