관련: 저장소 공유 · Query 실행 · 독립 결과 값

원리와 입력

메모리가 계속 증가할 때는 첫 프레임과 마지막 프레임에서 살아 있는 영상, ROI, 모델, Query 실행 및 캡처의 수를 비교해 보세요. 원본만 닫고 각 프레임의 결과 영상을 보관하면 저장소는 계속 참조될 수 있습니다. 반대로 결과가 갑자기 접근 불가라면 사용 중인 객체가 반환받은 독립 핸들인지, 이미 닫힌 원본 변수인지 확인해야 합니다.

적용과 확인

문제를 줄인 작은 사례로 재현할 때는 영상 생성, ROI 또는 Share 취득, 원본 종료, 남은 핸들 읽기, 남은 핸들 종료 순서를 기록합니다. 닫힌 객체 접근 오류는 연산의 픽셀 정확도와 다른 문제이므로 두 검사를 분리합니다. 관리형 환경에서는 using이나 with 범위가 반복문 안에 있는지 확인하고, 예외가 발생하는 경로도 같은 방식으로 정리되도록 작성하세요. 실제 회수량과 성능은 런타임과 작업 부하에 따라 측정해야 합니다.

적용할 때 살펴볼 점

카운트가 증가하는 객체를 찾았다면 해당 객체를 만든 호출의 반환 계약을 다시 확인하세요. 예를 들어 캡처 하나를 매 프레임 취득하지만 실행만 닫는다면 취득한 이미지의 종료가 별도로 필요할 수 있습니다. 반대로 독립 값 스냅샷은 핸들 누수의 원인으로 단정하지 말고 실제 소유 객체가 어디에 보관되는지 확인합니다.

같은 재현 입력을 유지하면서 한 번에 한 소유 객체의 종료 시점만 바꾸면 누가 참조를 보유하는지 좁혀 볼 수 있습니다. 종료된 핸들의 오류를 픽셀 값 오류와 섞지 말고 따로 기록합니다.
