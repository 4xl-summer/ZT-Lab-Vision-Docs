동일 SDK에서 패키지 만들기

Rust와 CPython 3.14 및 .NET 10 SDK가 설치된 Linux 환경에서 실행합니다. SDK_SOURCE와 PACKAGE_DIR은 실제 절대 경로로 바꾸세요. 두 생성 스크립트는 기존 배포물 덮어쓰기를 거부하므로 새 출력 폴더를 사용합니다.

Bash
export SDK_SOURCE=/absolute/path/ZT-Lab-Vision
export PACKAGE_DIR=/absolute/path/packages
cd "$SDK_SOURCE"
git checkout ce902e85c3405eb63df40c699ddbdf70ee1d03bd
cargo build -p zvision-ffi --release --locked
export NATIVE_LIBRARY="$SDK_SOURCE/target/release/libzvision_ffi.so"
python3.14 scripts/build-python-package.py --output-dir "$PACKAGE_DIR" --native-library "$NATIVE_LIBRARY"
python3.14 scripts/build-nuget-package.py --output-dir "$PACKAGE_DIR" --native-library "$NATIVE_LIBRARY"

사용자가 Cargo 출력 경로를 변경했다면 NATIVE_LIBRARY도 실제 Release 파일 위치로 지정하세요. wheel에는 네이티브 파일과 제3자 고지가 포함됩니다. Linux wheel은 해당 호스트 형식이며 manylinux 호환성을 별도로 주장하지 않습니다.

원리와 입력

로컬 패키지를 생성할 때 SDK_SOURCE와 PACKAGE_DIR은 실제 절대 경로여야 하며 기존 배포물과 충돌하지 않는 새 출력 폴더를 사용합니다. 먼저 지정된 SDK 리비전에서 locked Release 네이티브 라이브러리를 만들고, 실제 산출물 경로를 NATIVE_LIBRARY에 지정합니다. Cargo 출력 위치를 바꾸었다면 예제의 기본 경로도 함께 바뀝니다.

적용과 확인

그다음 wheel과 NuGet 생성 스크립트에 같은 네이티브 파일을 전달합니다. 이 과정은 소스 참조 실행이 아니라 소비할 배포물을 만드는 단계입니다. 빌드된 래퍼와 네이티브 버전이 다르면 로딩 또는 호출 결과가 어긋날 수 있으므로 동일 SDK 기준을 유지하세요. 명령의 checkout이나 빌드는 작업 트리와 환경에 영향을 줄 수 있으므로 대상 저장소와 위치를 스스로 확인한 뒤 실행해야 합니다. 생성 후에는 별도 소비 환경에서 설치와 실행을 검증합니다.

읽기와 적용

두 패키지 생성 명령은 같은 Release 네이티브 산출물을 입력으로 받습니다. 먼저 빌드가 성공했는지와 해당 경로에 호스트용 파일이 있는지 확인한 다음 각각의 출력물을 설치 환경으로 가져갑니다. 패키지 생성 성공은 별도 소비 프로젝트에서 실제 호출이 성공했다는 의미까지 포함하지 않으므로, 다음 단계에서 격리된 설치와 결과 비교를 수행합니다. 이 절차에 제시된 checkout 명령은 선택된 작업 트리의 상태를 바꾸므로 개인 변경사항이 있는 체크아웃과 구별해 읽어야 합니다.
