대기열과 취소

ZInspectionHost는 단일 작업자와 유한 대기열을 사용합니다. capacity 기본 2, 범위 1–16이며 실행 중인 작업은 용량에 포함하지 않습니다. Submit의 frameId와 recipeVersion은 양수입니다. Accepted에는 완료 Task가 있고 QueueFull 또는 Closed에는 없습니다. 수락 시 입력을 독립 임대하고 완료 시 해제합니다. 완료된 결과는 호출자가 해제합니다. 취소는 대기 중 또는 단계 사이에 적용되며 진행 중인 네이티브 호출을 강제 중단하지 않습니다. UI 스레드에서는 StopAsync로 정리를 기다립니다.

ZInspectionHost는 단일 작업자와 유한한 대기열로 입력을 처리합니다. 기본 용량은 2이고 허용 범위는 1부터 16이며, 현재 실행 중인 요청은 대기열 용량에 포함되지 않습니다. 제출할 때 프레임과 레시피 세대는 각각 양수여야 합니다. 수락된 요청은 입력 영상 데이터의 독립 임대를 보유하고 완료 작업을 돌려주지만, 대기열 포화나 종료 상태에서는 완료 작업이 없는 거절 상태가 반환됩니다.

대기 중 취소와 실행 단계 사이의 취소는 요청을 정리하는 데 사용되지만 이미 진행 중인 네이티브 실행을 강제로 중단하지는 않습니다. 완료 실행 결과는 실행자가 해제해야 합니다. 종료 시에는 새 제출을 막고 남은 임대가 정리될 때까지 기다립니다. UI 스레드에서 동기적으로 기다리면 화면이 멈출 수 있으므로 제공되는 비동기 종료 흐름을 사용합니다.

예를 들어 용량 2의 대기열이 이미 두 요청으로 찼다면 새 요청은 QueueFull로 거절될 수 있으며 그 요청의 Completion은 없습니다.

수락부터 종료까지의 소유권

Submit에 넘기는 영상은 호출자 소유이고 호스트는 요청을 수락할 때 별도 공유 임대를 얻습니다. frameId와 recipeVersion은 양수이며 레시피는 해당 요청에 적용할 불변 설정입니다. Accepted라면 Completion 작업이 있고 그 완료 결과를 받은 쪽이 ZInspectionResult를 해제합니다. QueueFull 또는 Closed라면 요청이 수락되지 않았으므로 Completion은 없습니다.

용량은 대기 중인 요청의 수에 적용됩니다. 예를 들어 capacity가 2이면 이미 실행 중인 한 요청 외에 두 요청이 대기할 수 있습니다. 대기열이 찼을 때 새 입력을 버릴지 나중에 다시 제출할지는 호출자의 정책이며, 이 호스트가 거절된 영상의 검사 결과를 대신 만들어 주지는 않습니다. 입력 순서와 세대를 기록하면 어느 프레임이 실제로 처리됐는지 추적할 수 있습니다.

취소 토큰은 대기 중인 요청과 실행 단계 사이에서 관찰됩니다. 이미 진행 중인 네이티브 호출을 중간에서 강제로 중단한다는 의미는 아닙니다. StopAsync는 새 요청을 닫고 취소를 전달한 후 작업자 정리를 기다립니다. UI에서는 비동기로 완료를 기다리고, 완료 결과를 받았다면 취소 여부와 관계없이 자신이 획득한 소유 객체를 정리합니다.

상태Completion호출자가 할 일
Accepted작업 있음완료·오류·취소 처리
QueueFull없음재시도 또는 폐기 정책 적용
Closed없음종료 상태 처리
