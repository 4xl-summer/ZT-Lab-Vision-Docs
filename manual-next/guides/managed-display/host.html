대기열과 취소

ZInspectionHost는 단일 작업자와 유한 대기열을 사용합니다. capacity 기본 2, 범위 1–16이며 실행 중인 작업은 용량에 포함하지 않습니다. Submit의 frameId와 recipeVersion은 양수입니다. Accepted에는 완료 Task가 있고 QueueFull 또는 Closed에는 없습니다. 수락 시 입력을 독립 임대하고 완료 시 해제합니다. 완료된 결과는 호출자가 해제합니다. 취소는 대기 중 또는 단계 사이에 적용되며 진행 중인 네이티브 호출을 강제 중단하지 않습니다. UI 스레드에서는 StopAsync로 정리를 기다립니다.

ZInspectionHost는 단일 작업자와 유한한 대기열로 입력을 처리합니다. 기본 용량은 2이고 허용 범위는 1부터 16이며, 현재 실행 중인 요청은 대기열 용량에 포함되지 않습니다. 제출할 때 프레임과 레시피 세대는 각각 양수여야 합니다. 수락된 요청은 입력 이미지의 독립 임대를 보유하고 완료 작업을 돌려주지만, 대기열 포화나 종료 상태에서는 완료 작업이 없는 거절 상태가 반환됩니다.

대기 중 취소와 실행 단계 사이의 취소는 요청을 정리하는 데 사용되지만 이미 진행 중인 네이티브 호출을 강제로 중단하지는 않습니다. 완료 검사 결과는 호출자가 해제해야 합니다. 종료 시에는 새 제출을 막고 남은 임대가 정리될 때까지 기다립니다. UI 스레드에서 동기적으로 기다리면 화면이 멈출 수 있으므로 제공되는 비동기 종료 흐름을 사용합니다.

가령 용량 2인 대기열이 이미 두 요청으로 찼다면 새 요청은 QueueFull로 거절될 수 있으며 그 요청의 Completion은 없습니다.

늦게 도착한 결과를 다루기

화면에서 입력이나 설정이 바뀌는 동안 이전 검사 요청이 끝날 수 있습니다. 호스트는 요청마다 양의 frameId와 recipeVersion을 전달하며, 결과도 두 값을 보관합니다. 표시 쪽에서는 기대 세대를 갱신한 뒤 완성된 결과의 두 값이 현재 하한 이상인지 확인할 수 있습니다. 과거 결과가 완료되었다는 사실만으로 현재 선택된 입력의 화면에 표시할 근거가 되지는 않습니다.

대기열 capacity의 기본값은 2이고 범위는 1부터 16입니다. 실행 중인 요청은 대기 용량에 포함되지 않으므로 capacity를 전체 동시 작업 수라고 해석하지 않습니다. Accepted면 결과 작업을 기다리고 QueueFull이면 완료 작업 없이 거절됩니다. 화면에서 연속 설정 변경을 처리할 때에는 거절이나 취소 상태를 숨기기보다 현재 화면이 어느 세대의 결과인지 표시하는 정책을 세웁니다.

결과를 표시하지 않기로 결정한 경우에도 완료 결과가 소유한 단계 영상은 정리해야 합니다. 이미 CreateDisplayFrame으로 독립 프레임을 얻었다면 그 프레임 또한 별도로 해제합니다. 취소는 네이티브 호출을 강제 종료하지 않으므로 닫기 과정에서는 StopAsync의 완료를 기다려 작업과 임대가 정리되도록 합니다.
